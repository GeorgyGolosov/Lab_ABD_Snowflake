# Условие лабораторной работы

## Анализ больших данных — лабораторная работа № 1 — нормализация данных в «Снежинку»

Одна из задач data engineer при работе с данными Big Data — трансформировать
исходную модель данных источника в аналитическую модель данных. Аналитическая
модель данных позволяет исследовать данные и принимать на основе полученных
данных решения. Классическими универсальными схемами для анализа данных
являются «Звезда» и «Снежинка». В лабораторной работе необходимо выполнить
трансформацию исходных данных в модель «Снежинка».

### Что необходимо сделать?

Необходимо данные источника (файлы mock_data.csv с номерами), которые представляют информацию о покупателях, продавцах, поставщиках, магазинах, товарах для домашних питомцев трансформировать в модель снежинка/звезда (факты и измерения с нормализацией).

# Инструкция по запуску

Для запуска необходимы Docker, Docker Compose и DBeaver.

1. Клонировать репозиторий и перейти в его директорию:

   ```bash
   git clone https://github.com/GeorgyGolosov/Lab_ABD_Snowflake.git
   cd Lab_ABD_Snowflake
   ```

2. Запустить PostgreSQL:

   ```bash
   docker compose up -d
   ```

3. Открыть DBeaver и создать подключение к PostgreSQL со следующими
   параметрами:

   | Параметр | Значение |
   |---|---|
   | Host | `localhost` |
   | Port | `5432` |
   | Database | `petstore` |
   | User | `postgres` |
   | Password | `postgres` |

4. После подключения открыть в DBeaver редактор SQL и последовательно выполнить
   скрипты из директории `sql/`:

   1. `00_create_staging.sql` — создание staging-таблицы;
   2. `02_analysis.sql` — анализ загруженных данных;
   3. `03_ddl.sql` — создание схемы «Снежинка»;
   4. `04_dml.sql` — заполнение справочников, измерений и таблицы фактов;
   5. `05_validation.sql` — проверка результата;
   6. `06_analytics.sql` — выполнение аналитических запросов.

   Импорт десяти CSV-файлов выполняется скриптом `01_import.sh` при запуске
   контейнера. После этого остальные SQL-скрипты можно открыть и прогнать в
   DBeaver в указанном порядке.


# Ход выполнения работы

## 1. Развёртывание базы данных

Для запуска PostgreSQL использовался файл
[`docker-compose.yml`](./docker-compose.yml). В нём настроены:

- образ `postgres:16`;
- база данных `petstore`;
- пользователь `postgres` с паролем `postgres`;
- публикация порта `5432`;
- постоянный Docker-том для данных PostgreSQL;
- подключение директории с CSV-файлами к `/data`;
- подключение директории со скриптами к `/docker-entrypoint-initdb.d`;
- проверка готовности базы командой `pg_isready`.

После выполнения `docker compose up -d` контейнер запускается, а к базе можно
подключиться через DBeaver. Далее скрипты открываются в SQL Editor и выполняются
в порядке их нумерации.

## 2. Создание staging-таблицы

Первым применяется скрипт
[`sql/00_create_staging.sql`](./sql/00_create_staging.sql). Он создаёт таблицу
`raw_data`, содержащую все 50 полей исходного CSV и дополнительное поле
`file_id`.

Все исходные столбцы имеют тип `TEXT`. Такое решение позволяет сначала загрузить
данные без ошибок преобразования, а приведение к `INTEGER`, `DECIMAL` и `DATE`
выполнить позднее при заполнении целевой модели.

В каждом CSV диапазон `id` повторяется от 1 до 1000. Поэтому первичный ключ
staging-таблицы является составным:

```sql
PRIMARY KEY (file_id, id)
```

Скрипт можно выполнять повторно, поскольку таблица создаётся с условием
`IF NOT EXISTS`.

## 3. Импорт исходных CSV-файлов

Импорт выполняется скриптом [`sql/01_import.sh`](./sql/01_import.sh). В нём
задан список из 10 CSV-файлов. Перед загрузкой каждого файла для столбца
`file_id` устанавливается значение от 0 до 9, после чего выполняется команда
`\copy`.

Таким образом, все исходные данные загружаются в одну таблицу, но строки из
разных файлов остаются различимыми. После завершения импорта значение по
умолчанию для `file_id` удаляется. Результат этапа — 10 000 строк: по 1000 строк
для каждого файла.

## 4. Разведочный анализ данных

После импорта выполняется скрипт
[`sql/02_analysis.sql`](./sql/02_analysis.sql). Он позволяет проверить структуру
и качество исходных данных до проектирования таблиц.

Скрипт определяет:

- общее количество строк в `raw_data`;
- количество строк для каждого `file_id`;
- количество уникальных покупателей, продавцов, товаров, магазинов и
  поставщиков;
- наличие пустых email покупателей, дат и сумм продаж;
- количество уникальных стран из полей покупателей, продавцов, магазинов и
  поставщиков;
- количество уникальных категорий товаров.

В результате анализа было установлено, что в `raw_data` находится 10 000 строк,
ключевые поля заполнены, в данных присутствует 230 стран и 3 категории товаров.
Email покупателей и продавцов не повторяются — найдено по 10 000 уникальных
значений.

Также анализ показал, что одинаковому `id` в разных файлах соответствуют разные
сущности. Поэтому для покупателей, продавцов, товаров и продаж применяется
глобальный ключ:

```text
global_id = file_id * 1000 + source_id
```

Такая формула формирует уникальные значения от 1 до 10 000 и предотвращает
объединение записей из разных файлов.

## 5. Создание схемы «Снежинка»

Структура целевой модели создаётся скриптом
[`sql/03_ddl.sql`](./sql/03_ddl.sql). В нём определены три типа таблиц.

Справочники:

- `dim_country` — страны;
- `dim_city` — города, регионы и ссылка на страну;
- `dim_category` — категории товаров.

Измерения:

- `dim_customer` — покупатели и сведения об их питомцах;
- `dim_seller` — продавцы;
- `dim_product` — товары и их характеристики;
- `dim_store` — магазины;
- `dim_supplier` — поставщики.

Таблица фактов `fact_sales` хранит дату продажи, количество, итоговую стоимость
и внешние ключи на все пять измерений.

Таблицы создаются в порядке зависимостей: сначала справочники, затем измерения и
в конце таблица фактов. В DDL используются `PRIMARY KEY`, `FOREIGN KEY`,
`UNIQUE`, `NOT NULL` и `CHECK`. Для внешних ключей и даты продажи созданы
индексы. Все таблицы и индексы создаются с `IF NOT EXISTS`, поэтому DDL можно
безопасно повторно выполнить в DBeaver.

## 6. Наполнение схемы данными

Перенос данных из staging-слоя выполняется скриптом
[`sql/04_dml.sql`](./sql/04_dml.sql). Перед загрузкой целевые таблицы очищаются
командой `TRUNCATE ... RESTART IDENTITY CASCADE`, после чего данные вставляются
в порядке внешних ключей.

Этапы DML-загрузки:

1. `dim_country` заполняется объединением уникальных стран покупателей,
   продавцов, магазинов и поставщиков. Для удаления повторов используется
   `UNION`.
2. `dim_city` заполняется уникальными городами магазинов и поставщиков. Через
   `JOIN` с `dim_country` каждому городу назначается `country_id`. Для
   поставщиков, у которых в CSV отсутствует регион, используется значение
   `(unknown)`.
3. `dim_category` заполняется уникальными значениями `product_category`.
4. `dim_customer`, `dim_seller` и `dim_product` получают глобальные ключи по
   формуле `file_id * 1000 + source_id`. Страны и категории заменяются внешними
   ключами на соответствующие справочники.
5. `dim_store` и `dim_supplier` получают детерминированные ключи, вычисленные
   функцией `hashtext()` по полной комбинации атрибутов. Через `JOIN` с
   `dim_city` сохраняется ссылка на город.
6. `fact_sales` заполняется последней. Каждая строка staging-слоя соединяется с
   `dim_customer`, `dim_seller`, `dim_product`, `dim_store` и `dim_supplier`.

Поскольку staging-данные хранятся как текст, в DML выполняется приведение типов:

```sql
NULLIF(value, '')::INTEGER
NULLIF(value, '')::DECIMAL(10,2)
TO_DATE(NULLIF(value, ''), 'MM/DD/YYYY')
```

`NULLIF` заменяет пустую строку на `NULL` и предотвращает ошибку преобразования
пустого текста в число или дату.

## 7. Проверка результата

После загрузки выполняется скрипт
[`sql/05_validation.sql`](./sql/05_validation.sql). В нём предусмотрены
автоматические контрольные точки:

- в `raw_data` должно находиться ровно 10 000 строк;
- должны присутствовать 10 значений `file_id` по 1000 строк;
- в `fact_sales` должно находиться ровно 10 000 фактов;
- внешние ключи всех пяти измерений должны быть заполнены.

Проверки реализованы в блоке `DO`. Если условие нарушено, вызывается
`RAISE EXCEPTION`, и выполнение останавливается. После успешной проверки скрипт
выводит количество строк во всех таблицах, число уникальных дат и суммарную
выручку.

Контрольные запросы показали:

## 8. Выполнение аналитических запросов

Последним выполняется скрипт
[`sql/06_analytics.sql`](./sql/06_analytics.sql). Он подтверждает, что созданная
модель пригодна для анализа и что связи между фактами, измерениями и
справочниками работают корректно.

В скрипте реализованы следующие запросы:

1. топ-10 стран покупателей по выручке;
2. количество продаж и выручка по категориям товаров;
3. топ-10 городов магазинов по выручке;
4. динамика продаж по месяцам и категориям;
5. топ-5 продавцов по выручке.

Для получения атрибутов справочников запросы проходят по нескольким уровням
связей. Например, страна покупателя определяется через цепочку
`fact_sales → dim_customer → dim_country`, а страна магазина — через
`fact_sales → dim_store → dim_city → dim_country`. Это и демонстрирует
особенность аналитических запросов к схеме «Снежинка».

## Итоговая ER-диаграмма

![ER-диаграмма схемы «Снежинка»](./Схема%20БД.png)

Центром модели является таблица `fact_sales`. Она содержит дату продажи, меры
`quantity` и `total_price`, а также внешние ключи на пять измерений.

На диаграмме представлены следующие цепочки связей:

- `fact_sales → dim_customer → dim_country`;
- `fact_sales → dim_seller → dim_country`;
- `fact_sales → dim_product → dim_category`;
- `fact_sales → dim_store → dim_city → dim_country`;
- `fact_sales → dim_supplier → dim_city → dim_country`.
